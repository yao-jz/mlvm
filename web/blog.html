Inside MLVM / An illustrated walkthrough

Finding one wrong instruction in 14.8 billion

We ran SmolLM2-135M inside MLVM and deliberately changed one result among 14.8 billion instructions. In a local test, 34 comparisons found the changed step. A referee then checked that single step from a saved record, without running the model again.

Jianzhu Yao (@alexbert135) and Pramod Viswanath · Princeton University · 22 October 2026

What MLVM does

  • It runs a compiled program in a RISC-V virtual machine, including floating-point arithmetic in software. With the same program and inputs, machines should agree on every bit of the result. CI checks the decoder demo across six platforms.
  • It can summarize the machine's state at any instruction with a 32-byte hash. If two runs start alike but end differently, a search narrows the disagreement to one instruction. A local referee checks that step when it is supported.
  • The current implementation is a local research prototype. It cannot yet settle single-precision arithmetic on a blockchain, and no complete dispute system is deployed. The measured BERT runs are roughly a thousand times slower than native code.
Four terms used throughout this article
Instruction
One operation the virtual machine executes, such as adding numbers or reading memory.
State root
A short hash of the machine's state. It acts as a fingerprint of its memory, registers and other tracked values.
Bisection
Binary search over two runs. Compare the midpoint, keep the half containing the disagreement, then repeat.
Witness
The state information supplied to the referee, together with memory proofs, so it can check one instruction.

1The problem

Suppose someone runs a language model for you and sends back an answer. You know which model, weights and prompt they were supposed to use. How do you check that they actually ran that computation? The same question comes up when auditing a benchmark or paying for an inference: the output alone does not tell you how it was produced.

You could run the model again, provided you trust the machine doing the check and can afford another inference. But even matching outputs leave a gap. In the experiments below, we changed individual instruction results and often got exactly the same text back. The computation had changed; the answer had not.

Optimistic verification, used in blockchain fault proofs such as Truebit, Arbitrum, Cannon and Asterisc, reduces the work required of a referee. Two parties run the computation and report a hash of the final machine state. If they disagree, the referee asks for the hash halfway through each run. If those hashes match, the disagreement is in the second half; otherwise, it is in the first. Repeating this search leaves one instruction to check, after about log2 N rounds for a run of N steps. Both parties still run the program. The referee checks only the disputed step. MLVM demonstrates this process locally; a complete on-chain dispute system is not built yet.

This requires honest machines to agree bit for bit. Floating point makes that harder, which is why Asterisc, the RISC-V fault-proof VM that MLVM builds on, left it out. Its ISA notes explain the decision:

RV{32,64}{D,F,Q}: no-op: No floating points support (since no IEEE754 determinism with rounding modes etc., nor worth the complexity)

ethereum-optimism/asterisc

That omission is expensive for neural networks. In the five BERT-family encoders we ran, 58 to 69% of instructions were floating-point arithmetic, loads or stores. An integer-only target can still run these models by compiling each float operation into an integer routine. In our matrix-multiplication comparison, that took 25 times as many instructions (§8.4). MLVM adds floating-point instructions to Asterisc and implements them in software, so their behavior does not depend on the host CPU. This article explains that implementation and the disputes we tested with it.

Why use a RISC-V virtual machine?

To settle a disagreement, both parties and the referee need an exact definition of a step. RISC-V gives us a common instruction set with operations small enough to check individually: add two values, read memory, take a branch. C and Rust compilers already target it. That lets us run compiled inference code, including the code that loads inputs and prepares the answer, through the same machine.

The RISC-V executable runs inside MLVM, so the host does not need a RISC-V processor. MLVM supplies the arithmetic, memory and system-call behavior. Keeping those rules fixed lets the same executable run on different hosts and gives the referee a precise transition to check. The cost is interpretation overhead; the measurements and limitations describe that tradeoff.

Starting from Asterisc

The integer RV64 interpreter, the Merkle memory, the Go state oracle (slow) and the Solidity step function (RISCV.sol) come from Asterisc, by protolambda and Optimism. MLVM added floating point and SoftFloat, the committed file system and its proofs, deterministic randomness, the syscalls that static glibc and Rust std need, and a way to include the answer in the final state. The dispute simulator, profiler and browser playground let us test and inspect those additions on actual model runs.

2From a model run to a disputed step

The program running inside the VM is called the guest. It is a statically linked RISC-V executable (an ELF file), built from C with GCC or from Rust with rustc. The Rust model guests use Hugging Face's Candle and tokenizers. Before execution, MLVM loads the program and its files, including the weights, tokenizer and prompt, into the guest's address space.

MLVM can hash the machine state into a 32-byte value, called a state root. This is a commitment: it lets another party check that a supplied piece of state belongs to that machine state. We call the initial hash the prestate root and the hash after the program halts the poststate root. The former identifies the computation's starting point; the latter includes what the program left in memory, including its answer if the program stored it there.

The first byte of every state hash is replaced by a status code: 0 for halted normally, 1 for invalid, 2 for panicked, 3 for still running. The demo's prestate begins 0x03bd61b5… and its poststate 0x00beedb0…, so a contract can read the outcome of a run without decoding anything.

If two runs start with the same root but finish with different roots, the referee uses the binary search described above, also called bisection. To check the remaining instruction, it needs a witness: an encoding of the state before the step, plus proofs for the memory that step reads or writes. These fit in a small dispute record. Anyone with the record can repeat that single-step check without loading the model or replaying the full run. The record contains the parties' claims about the search; checking it does not independently establish that either full run happened as claimed.

How the components fit together in the implementation

For a first pass, you can go straight to how the search works or what happened in the experiments. The next sections explain the implementation.

3Making floating-point math repeatable

These models represent weights and intermediate values as floating-point numbers. MLVM needs each operation to produce the same bits on every host, including its rounding and exception flags.

3.1 Why a Go float addition is not enough

A Go interpreter could execute fadd.s as a Go float32 addition. That handles ordinary inputs in the usual rounding mode, but implementing a RISC-V instruction also means reproducing its rounding rules, exception flags and special cases. A plain Go addition does not give the interpreter control over all of those:

  • Rounding is per instruction. A RISC-V float instruction carries a 3-bit rm field that selects one of five rounding modes for that instruction alone, or the dynamic mode in frm. Go has no way to set the host's rounding mode, let alone per instruction.
  • Exception flags are architectural state. Invalid, divide-by-zero, overflow, underflow and inexact accumulate in fflags, and a program can read them. They have to be computed exactly, and they are committed.
  • NaNs differ. RISC-V requires the canonical NaN. Hosts differ in how they propagate NaN payloads, and the WebAssembly specification explicitly leaves the sign and payload bits of a NaN result nondeterministic.
  • The Go compiler may fuse. The Go specification allows an implementation to combine x*y + z into one fused multiply-add, so the same Go source can round once on arm64 and twice on amd64.
  • RISC-V has its own rules. Single-precision values are NaN-boxed inside 64-bit registers. fmin and fmax order −0 below +0 and return the non-NaN operand. Out-of-range conversions saturate.

MLVM therefore implements guest float arithmetic with integer operations. The host CPU's floating-point unit does not determine the result.

3.2 SoftFloat in Go

MLVM implements all 62 instructions in RISC-V's F and D extensions, for single- and double-precision floating point. The arithmetic comes from rvgo/comp, a hand port of Berkeley SoftFloat Release 3e to Go. It has 121 files and about 5,800 lines, or about 6,100 including support types and RISC-V-specific NaN handling. fast/vm.go decodes each instruction and calls the corresponding operation. Before that call, it selects the rounding mode:

Code: selecting the rounding mode

rvgo/fast/vm.go

// The rounding mode comes from the instruction's rm field, except that rm == 7 means
// "dynamic": use frm from the CSR. RISC-V's rm encoding and Berkeley's rounding-mode
// numbering agree on 0..4 (RNE, RTZ, RDN, RUP, RMM), so no translation is needed.
beginFloatOp := func(rm U64) {
    mode := rm
    if mode == 7 {
        mode = and64(shr64(toU64(5), s.FCSR), toU64(0x7))
    }
    if gt64(mode, toU64(4)) != 0 {
        revertWithCode(0xbadf1041, fmt.Errorf("reserved rounding mode: %d", mode))
    }
    Softfloat_exceptionFlags = 0
    Softfloat_roundingMode = uint8(mode)
}

After the operation, the VM merges any exception flags raised by SoftFloat into fcsr, the floating-point control and status register. It occupies 8 bytes in the state witness. A reserved rounding mode causes the step to fail. Single-precision reads also check NaN-boxing: a 32-bit value in a 64-bit float register must have all its upper bits set to 1. Otherwise, the read returns a canonical NaN: 

unboxF32 := func(v U64) uint32 {
    if v&0xFFFF_FFFF_0000_0000 != 0xFFFF_FFFF_0000_0000 {
        return 0x7FC00000 // canonical single-precision NaN
    }
    return uint32(v)
}

The fused multiply-add needed one more step. Berkeley's mulAdd takes an operation field that negates either the product or the addend, but not both, while RISC-V has four variants. All four go through the plain operation with the signs of a and c flipped as needed. This is what the RISC-V reference implementation does, and it is safe on NaN operands because every NaN result is canonicalised.

3.3 Bugs the tests found

The F and D suites from riscv-tests initially passed 9 of 23 tests. After fixes, all 23 passed. Eleven failures had the same cause: the computed value was correct, but the port never raised exception flags and ignored frm. Those tests failed on an fsflags check. The remaining three exposed problems with fmin/fmax NaN selection and NaN-boxing.

We exclude the 21 rv32* suites from that count. On an RV64 machine, their register-width check exits successfully after about 68 steps, before running any float instructions. Counting those as passes would overstate coverage; the harness checks that they take this early exit.

We also compare the port with an independent implementation. TestSoftFloatAgainstNativeFPU checks it against the host FPU on 200,000 random operand pairs per operation, drawn toward subnormals, wide exponent gaps and exact ties. For + − × ÷ √ the correctly rounded result is unique, so any disagreement needs investigation. This test and the float sub-game's bit-exact test harness (§8.3) found defects in code that had already shipped:

  • F64_div rounded the wrong way on about 2% of inputs. The port had dropped a truncation that the C code has; the identical line eight statements earlier kept it. 
    - (uint64_t) doubleTerm * ((uint32_t) sigB >> 4);   /* Berkeley: truncate, then shift */
- uint64(doubleTerm)*uint64(sigB>>4)                // the port: shifted all 64 bits
  • F64_to_ui64 ignored its operand: it declared a variable, never assigned it, and converted the constant zero. fcvt.lu.d returned 0 for every input.
  • 0 × ∞ returned the canonical NaN without raising invalid. The value was right, so only a flags comparison could notice.

The conformance suites missed all three. The F64_div bug also survived the end-to-end determinism checks and five transformer models.

These bugs explain why we need both kinds of test. Comparing state roots across machines checks reproducibility, but the same arithmetic bug can produce matching roots everywhere. Comparing with an independent implementation checks the arithmetic itself.

3.4 Why native builds can still give different numbers

Correct instructions do not guarantee that two builds of the same source produce the same result. We saw this when fixing fused multiply-add. Previously, MLVM evaluated fmadd as a multiply followed by an add, rounding twice. The C MLP's result differed from a native run by about 13 units in the last place (ULP), a measure of the gap between nearby floating-point values. Rounding once reduced the difference to 1 ULP.

The five transformer scores stayed bit-identical after that fix. Their Candle kernels used separate multiplies and adds on the paths contributing to the score; Rust does not fuse a*b + c unless asked. The C MLP reaches libm routines that do use fused multiply-adds to evaluate polynomials, so it was affected.

In these runs, the remaining difference of 3 to 19 ULP did not track run length: bert-base executed 6.6 times as many instructions as MiniLM-L6, with the same 3 ULP gap. The builds also used different math libraries: glibc's erf, tanh and exp inside the guest, and Apple's libm natively. Those libraries, along with target-specific std code and compiler output, can account for differences even when individual instructions are correct.

This is why an MLVM dispute compares runs of the same executable. The math library is linked into that executable, so both parties use the same routines as well as the same model and inputs. Comparing a VM run with a separately compiled native build is useful for testing, but it is a different comparison.

4Keeping other inputs the same

Floating-point arithmetic is only part of the problem. A program can also change its behavior based on the clock, random bytes, available CPUs or files on the host. MLVM controls what the guest sees through its system calls. There is no guest kernel: ecall dispatches on the syscall number in a7. The fast VM recognises 37 Linux syscall numbers, answers 35 and refuses 2. That is enough for the static glibc and Rust std programs used here to start, allocate memory, read files and print.

These restrictions sometimes require changes to guest code. For example, Hugging Face tokenizers uses rayon to parallelise encode_batch. Rayon cannot create its thread pool here, so the call panics. Encoding sentences one at a time gives the same token IDs and avoids the thread pool. Another less obvious dependency is Rust's hash maps: they seed themselves from getrandom, which can affect the program's instruction count. The randomness bytes must therefore be part of the inputs both parties agree on.

The same program on different hosts

The native CLI runs on Linux, macOS and Windows. A WebAssembly build brings the same interpreter to the browser. Each host executes the same guest binary and staged inputs, with the same software arithmetic and system-call rules. This lets someone repeat a run or check its dispute record on a different computer.

To check this across hosts, .github/workflows/determinism.yml runs five prompts through the TinyStories guest on linux/amd64, linux/arm64, darwin/arm64, darwin/amd64, windows/amd64 and WebAssembly under Node. It fails unless all six produce the same prestate, step count and poststate. "Once upon a time" takes 38,186,542 instructions and ends in 0x00beedb0…97f9 on every platform. The merged table is published with the playground, which compares your browser's root against it.

5One fingerprint for the whole machine

A referee needs to check small pieces of a potentially large machine. The state root makes this possible: each supplied piece can be checked against the same hash.

5.1 The 674-byte state witness

To compute a state root, MLVM encodes the machine in a fixed 674-byte witness, hashes it with Keccak-256, then replaces the hash's first byte with the status code. The witness contains registers and control fields, plus roots for memory and the file system. It does not contain a copy of every byte in memory. Asterisc's witness was 362 bytes; MLVM added 312 for float registers, the randomness window, fcsr and the file-system root.

5.2 Memory: 264 bytes as a sparse Merkle tree

The guest sees a full 64-bit address space, but MLVM allocates only the 4 KiB pages it touches. A glibc "hello world" touches about 240 pages out of the possible 252. Memory is arranged in a binary Merkle tree: each leaf holds 32 bytes, and each parent hashes its two children. The root commits the contents of the whole address space. To check one leaf, the referee needs that leaf and the sibling hashes along its path to the root, rather than all of memory.

The implementation avoids hashing empty or unchanged memory. An unallocated subtree uses zeroHashes[depth], computed once. A write marks the nodes on its path to the root as stale; those paths are recomputed only when a root is requested. On an Apple M3 Max, recomputing the root of a 1 MiB working set from scratch takes about 31 µs, and one proof against a warm cache about 7 µs.

Proof order must match the contract's expectations. trackMemAccess checks that proofs are appended in the order the verifier consumes them, and verifyMemChange checks that a write targets the word covered by its proof. Both panic on a mismatch, so these mistakes are caught during proof generation.

5.3 Files are committed state too

The model's weights need the same protection as the program's memory. Otherwise, two machines could claim the same starting state while reading different files. At load time, each file is placed in its own 64 GiB-aligned slot starting at 0x2000_0000_0000_0000, and openat, read and lseek are served straight out of Merkle memory. The bytes are covered by the memory root. The metadata (which name maps to which address and size, which descriptors are open, and at what offset) is bound by the last 32 bytes of the witness, through two fixed-depth trees of 1,024 leaves each: a file index sorted by name, and a descriptor tree indexed by fd.

Encoding: file and descriptor commitments

docs/ARCHITECTURE.md · integers are unsigned 64-bit big-endian

fileID         = keccak256(path bytes)

A file syscall carries a fixed 992-byte proof: the five-word header, one file leaf with its ten siblings, and one descriptor leaf with its ten siblings. The slow Go interpreter and RISCV.sol both authenticate it, so openat, a staged read, fcntl, lseek and close can be checked as individual state transitions. Keeping these proofs bounded imposes limits: files are read-only, names are at most 255 bytes, there are at most 1,024 files and descriptors, and a read moves at most 32 bytes. That last limit has a measurable cost. Candle's MiniLM spends 12.8% of its billion instructions reading staged files.

6Keeping the answer in the state

A dispute checks a transition between machine states. For that check to say anything about the model's answer, the answer has to remain in the final state. MLVM does not include the stdout stream in its state hash. A machine can therefore print a different answer and still finish with the honest machine's root.

MLVM guests write their answer into a fixed location in memory and leave it there. The window is 64 bytes and 64-byte aligned, so its two 32-byte leaves are siblings and a single 1,920-byte branch proves the whole answer against the poststate root.

A guest needs to store its answer in the result window for a verifier to check it against the final state. Printed output is useful to a person reading the run, but it is not a reliable record for this protocol.

7Finding one step among 14.8 billion

Each round cuts the search interval in half. A longer model run needs more work from the two machines, but only a few more questions from the referee.

7.1 Narrowing the interval

The search tracks two instruction counts, lo and hi. Both parties agree on the state after lo instructions and disagree after hi. Initially, lo = 0 and hi is the length of the longer run. Each round asks about the midpoint and cuts the interval in half, keeping one agreed state and one disputed state as its endpoints.

Code: the binary search loop

rvgo/internal/liar/game.go · errors elided

// Invariant: the parties agree on the state after lo instructions and disagree after hi.
lo, hi := uint64(0), max(honest.Steps(), liar.Steps())
for n := 1; hi-lo > 1; n++ {
    mid := lo + (hi-lo)/2
    h, _ := honest.HashAt(mid)
    l, _ := liar.HashAt(mid)
    r := Round{N: n, Lo: lo, Hi: hi, Mid: mid, Honest: h, Liar: l, Agree: h == l}
    honest.Observe(r)   // moves are public: each party pins its machine at lo
    liar.Observe(r)
    if r.Agree {
        lo = mid
    } else {
        hi = mid
    }
}
t, _ := honest.TransitionAt(lo)   // witness and proofs for instruction lo

A lie can change how long a run is (on MiniLM-L12 the liar's run was 16 instructions shorter, on bge-base 68 longer), which is why hi starts at the longer run. A party asked about a step after its own halt answers with its final hash. The number of questions is ⌊log₂ N⌋ or ⌈log₂ N⌉, whatever the program does.

7.2 Answering without replaying from the start

The referee does little work during this search, but the parties need to recover earlier states. Replaying from the start for every question would cost hundreds of billions of instructions for the SmolLM2 dispute. MLVM instead saves checkpoints and reuses the states reached during earlier rounds.

Checkpoints. During its run each party saves a copy of its machine every 222 = 4,194,304 instructions, and answers a question by replaying from the nearest copy at or before the step asked.

Sharing unchanged pages. Copying gigabytes of weights at every checkpoint would be too expensive. Memory.Clone copies the map of page pointers and the cached upper tree nodes while sharing the pages themselves. Ownership is tracked with epochs: every Memory has one, every page records the epoch that may write it in place, and both sides take fresh epochs at a clone. Every write goes through one function:

Code: copying a page on its first write

rvgo/fast/memory.go

// writablePage returns the page at pageIndex for writing. A page shared with a clone is
// first copied, together with its node cache, so the other Memory keeps seeing the old
// bytes. Every write to page data goes through here.
func (m *Memory) writablePage(pageIndex uint64) (*CachedPage, bool) {
    p, ok := m.pageLookup(pageIndex)
    if !ok || p.epoch == m.epoch {
        return p, ok
    }
    data := *p.Data
    own := &CachedPage{epoch: m.epoch, Data: &data, Cache: p.Cache, Ok: p.Ok}
    m.pages[pageIndex] = own
    ...
}

Beyond the page map and tree cache, a checkpoint needs separate storage only for pages that are changed. Read-only weights stay shared across all copies.

Bounded memory. A party keeps at most 64 copies. When a run would save a 65th, it doubles its interval and drops every other copy. A billion-instruction BERT run keeps 64 copies about 17 million instructions apart, and SmolLM2's 14.8 billion about 268 million apart.

Reusing the last agreed state. Every round is public, so each party knows the interval still in dispute. After an agreeing round a party keeps its machine at lo, and later questions replay only inside the interval. Each question therefore replays at most one checkpoint interval, and once the interval in dispute is shorter than that, at most the interval itself, which halves every round.

8Checking the disputed instruction

8.1 Recovering the instruction from the proof

At the end of bisection, the honest party supplies a 674-byte witness for the state before instruction lo, along with the memory proofs needed to execute it. The referee first hashes the witness and checks it against the root both parties agreed on. It then reads the program counter from the witness and recovers the instruction word from the memory proof. This prevents a party from supplying a different instruction while claiming to defend the same step:

Code: checking the instruction proof

rvgo/internal/liar/game.go · provenInstruction

leaf := memProof[:32]
node := common.BytesToHash(leaf)
path := pc >> 5
for i := 0; i < 64-5; i++ {                    // 59 siblings, leaf upward
    sibling := memProof[32*(i+1) : 32*(i+2)]
    if (path>>i)&1 == 0 {
        node = crypto.Keccak256Hash(node[:], sibling)
    } else {
        node = crypto.Keccak256Hash(sibling, node[:])
    }
}
if node != common.BytesToHash(sw[:32]) {       // witness bytes 0–31: the memory root
    return 0, fmt.Errorf("instruction proof does not match the witness memory root")
}

Then it executes that one instruction, by one of three routes.

MLVM has three execution paths. The fast interpreter runs whole programs; the other two check supported steps from a witness:

All three use the same small set of operations (add64, shr64, signExtend64, …). It is defined twice, once over Go uint64 in fast/yul64.go and once over 256-bit words in slow/yul256.go. The fast VM keeps riscvStep in a single function to make it easier to compare with the Yul implementation line by line. For every one of the 84 integer, multiply and atomic conformance suites, the three produce the same post-state hash, step for step. An average step costs about 84,000 gas and the worst 186,089.

The native CLI embeds RISCV.sol's compiled bytecode and runs it in an in-process EVM alongside slow.Step. CI checks that the embedded bytecode matches the contract source. In the gallery's disputes, an addi costs 47,888 gas, an fld that misread one bit 83,675 (its proof is 3,840 bytes, one branch for the fetch and one for the loaded word), and the sb that stored a forged token 131,482 to 131,569.

Keeping three implementations in step has a cost of its own. When the float registers grew the witness from 362 bytes, RISCV.sol still located its proof calldata with the literal 548, derived in a comment from the old layout. Every proof was rejected before a single instruction executed. The offset is now derived from stateSize().

8.3 Float arithmetic: SoftFloat re-execution

RISCV.sol carries the float registers but does not execute float arithmetic. A Yul port of SoftFloat would add several thousand lines of bit manipulation to the verifier and would need careful testing and review. The current referee checks float arithmetic locally. The OP-FP opcode (0x53) and the four fused multiply-add opcodes (0x43, 0x47, 0x4b, 0x4f) read and write only registers and fcsr, and all of those are in the witness. The referee builds a small machine with those registers and the proven instruction word, executes it once, writes the results back into a copy of the witness, and hashes it:

This check uses the same SoftFloat implementation as the fast VM, so it does not provide an independent check of that implementation or an on-chain verdict. MLVM also has an experimental on-chain route for f64, called nesting: compile one operation for RV64IMA, where it becomes an integer soft-float routine, and run that routine as a nested machine whose steps RISCV.sol can execute. Nested traces average 83 to 680 steps per operation, which adds 7 to 10 bisection rounds. It computes in round-to-nearest-even only, covers no f32, and is not bound to an outer game.

8.4 The cost of compiling floats into integer code

To measure the cost of the integer-only approach, we built the same Rust matrix multiplication (GEMM) program twice. It uses no_std, with no libc, allocator or libm, to isolate the cost of floating-point operations. For RV64IMAFD, MLVM executes fmul.d with SoftFloat. For RV64IMA, the compiler expands every float operation into integer code: __muldf3, __adddf3.

Each double-precision operation expands into about 91 integer instructions, the branchy exponent alignment, normalisation and rounding of __adddf3 and __muldf3. In the soft-float build the disputed step is the mulhu that forms the high half of the mantissa product, an integer instruction that RISCV.sol settles by itself. The price is 25 times the instructions to execute and bisect over, and five more questions.

The two builds show the tradeoff in this workload. Compiling floats into integer code lets the existing integer verifier check the disputed operation, but increases the instruction count by about 25 times. That also means more work when replaying a disputed interval. With F and D instructions, the trace is shorter, but float arithmetic needs its own verifier. Those instructions are also somewhat slower to interpret: bge-base runs at 19.6M instructions/s here, compared with about 25M for integer code.

8.5 The dispute record

A finished dispute can be saved as a JSON record (mlvm.dispute-record/1) of a few kilobytes. It contains the questions, both parties' answers, and the witness and Merkle proofs for the disputed instruction. A new referee can check whether those recorded claims are internally consistent and whether the supported disputed step is correct. The record alone cannot prove that either party ran the entire program as claimed. The referee checks:

  1. Each round asks about the midpoint of the interval still in dispute, starting from [0, max(steps)], and the rounds end with hi − lo = 1.
  2. The verdict's step is lo, and its agreed prestate and the two poststates are the answers both parties gave at lo and hi.
  3. The witness hashes to the agreed prestate, and its step field is lo.
  4. The first memory proof proves the instruction word against the witness memory root.
  5. Executing that one instruction gives the referee's poststate: SoftFloat for float arithmetic, slow.Step (and, natively, RISCV.sol in an EVM, which must agree) for everything else.
$ mlvm referee dispute.json
  ✓ 25 questions, each about the midpoint of the instructions still in dispute, narrow
    38,186,542 instructions to step 38,060,100.
  ✓ The 674-byte state witness hashes to the state both machines agreed on before it.
  ✓ The instruction word is proven by a Merkle proof against the witness's memory root.

    referee computes                     0x0307f3e7...  → honest wins

The tests tamper with a valid record by changing a question, an answer, a witness byte or a proof sibling, and require the referee to reject it. Checking the gallery records in the playground takes about a millisecond, including the SmolLM2 record. Its 34 rounds refer to a 14.8-billion-instruction run, but the referee only needs the record to repeat the local verdict on the disputed step.

9What happened when we changed one result

9.1 Finding a change that survives

To test bisection and the referee, we built a version of the VM that deliberately changes one result. We call it the liar. We ran it on the gallery's 13 programs, from a 263,030-instruction C program to SmolLM2-135M, with five kinds of change:

--lieThe lying machine…Ruled by
ulprounds one float result one unit in the last place the wrong waySoftFloat, from the witness
loadreads one bit of one loaded value wrong (a weight or an activation)RISCV.sol, slow.Step
intflips the lowest bit of one integer resultRISCV.sol, slow.Step
outputprints bytes it did not computeusually nothing: stdout is not state
commit, tokencommits an answer it did not computeRISCV.sol, slow.Step

Many small changes disappear before the program finishes. Rounding can absorb them, or a later write can overwrite the affected value. That leaves no difference in the final roots for bisection to find. To select a useful test case, the liar forks at a candidate instruction and runs two copies in lockstep: one unchanged, one with a bit flipped. It compares registers and every word either copy stores. When those match, it checks the full state hash as well, covering syscall writes, file state and the randomness cursor. If the states have converged, it abandons that candidate.

The liar keeps a change if it survives 2.5 million instructions, longer than one TinyStories forward pass (about 1.8 million). By then it has often reached data that later passes retain, such as the KV cache. This is only a heuristic. If the difference disappears later, or the program crashes, the liar starts again with the next candidate.

9.3 Different states can still produce the same answer

In the runs with a surviving arithmetic change, both TinyStories implementations still printed the original story. SmolLM2 printed and committed the same 16 tokens, MiniLM-L6 printed the same score to ten digits, and ieee printed the same digits. Their state roots differed, even though those outputs matched. On the larger BERTs, the change reached the committed score: bge-base went from 0.7760061622 to 0.7760063410, differing in the seventh decimal place. Comparing state roots detected all of these surviving changes; comparing displayed answers would have missed most of them.

9.4 Comparing the C and Candle decoders

The TinyStories checkpoint runs twice in the gallery: as the llama2.c-style C decoder (38.2 million instructions, hand-written loops with fused multiply-adds) and through Candle's llama2_c model (122.2 million, separate multiplies and adds in a general gemm). Despite rounding differently, they chose the same 16 tokens on all three prompts we tried. In the measured SmolLM2 run, single-threaded SoftFloat execution also chose the same 16 tokens as native Candle with NEON and threads. Greedy decoding tolerated the numerical differences in these examples. Matching tokens still does not imply matching execution, which is why the dispute compares two runs of the same VM executable.

10Where the instructions go

Since the interpreter sees every instruction, it can count them exactly. mlvm xray records those counts by function, which helped explain several unexpected costs in the model runs below. These are instruction counts, not elapsed time: an operation's share of the profile does not necessarily equal its share of runtime.

The profiler decodes each PC's instruction word once. Its disassembler agrees with GNU objdump on every instruction in the embedded guests. It tracks calls with a shadow stack: a jal or jalr that links through ra or t0 pushes a frame, jalr zero, 0(ra) pops one, and a jump into another function replaces the top frame. The poststate is identical with and without profiling, and Rust symbols are demangled.

11The same machine in a browser tab

The playground uses the same Go packages as the CLI. rvgo/wasm compiles them with GOOS=js GOARCH=wasm into a 10 MB module (4 MB gzipped) that embeds the TinyStories guest, weights and tokenizer. Each party runs in its own Web Worker, and the computation stays in the browser.

On an Apple M3 Max in Chrome, the 38-million-instruction TinyStories run takes about 8 seconds with profiling on (5.3 million instructions per second). The native CLI takes about 1.2 seconds. A lying run in the browser takes about 9 seconds, and bisection takes about 5 with both parties answering in parallel. Each party keeps up to eleven machine copies, about 90 MB, and half as many on small devices.

The browser build leaves out the EVM, so integer verdicts there use slow.Step only. The WebAssembly build is one of the six in the determinism matrix, and CI plays a full dispute across three WebAssembly instances in Node worker threads, failing unless bisection lands on the lie.

12Limits

The experiments above exercise individual verification components and a local dispute simulation. Several gaps remain before they can form a complete protocol; docs/STATUS.md tracks them.

  • There is no complete, deployed dispute game. The local simulation and experimental contracts do not yet provide bonds, timeouts, a challenge period or challenger services.
  • f32 arithmetic cannot be settled on chain. The nested f64 route is experimental and round-to-nearest-even only, and real code rounds otherwise: glibc's expm1, reached from the C MLP's tanh, executes fcvt.w.d …, rtz.
  • Syscall coverage is incomplete in the verifiers. The fast VM answers 35 syscalls, slow mirrors 22 and RISCV.sol 27, and they disagree on getrandom: the fast VM serves committed bytes, slow reverts, and RISCV.sol treats it as a no-op. No complete glibc or Rust std trace replays end to end in either verifier. The disputes above end on instructions the verifiers do support.
  • Execution is much slower than native inference. On the BERT models MLVM is 673 to 1,627 times slower than native Candle on the same machine: interpretation retires about 20 million instructions per second, and the guest runs scalar code where native Candle uses SIMD.
  • Large-model disputes need several gigabytes of memory. A dispute over a 110M-parameter model peaks at 8 to 9 GB, over SmolLM2-135M at about 10 GB.
  • It is unaudited, pre-1.0 research software. Formats and interfaces may change.

13What comes next

  • The vector extension. Supporting vector instructions would let guest kernels process several values per instruction. Its effect on execution and proof costs still needs to be measured.
  • Half precision (Zfh). SoftFloat's f16 operations are already ported; the instruction decoder still needs to call them. This would allow guests to use half-precision arithmetic directly.
  • Settling f32. Nested single-precision operations with NaN-boxed results, and binding the disputed outer instruction, its operands and its result to the nested game.
  • Syscall equivalence. Make randomness and every remaining syscall agree across the three implementations, with trace-level differential tests sampled from complete guests.
  • A complete dispute protocol. RISCV.sol's step() already matches the OP Stack's IBigStepper signature. Integration still needs the game rules, bonds, timeouts and challenger services described above.
